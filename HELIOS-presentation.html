Qu'est-ce que HELIOS ?

HELIOS est une plateforme AIOps (Artificial Intelligence for IT Operations) qui surveille en continu un cluster Kubernetes, détecte les incidents automatiquement grâce à un moteur d'intelligence artificielle, en explique la cause racine en langage naturel, puis applique la correction (redémarrage, scaling, bascule…) via des workflows automatisés — avec ou sans validation humaine selon le niveau de risque, et notification par e-mail.

👁️ Observer

Collecte continue des métriques (Prometheus, cAdvisor, kube-state-metrics) et des logs (Loki) de tout le cluster.

🧠 Comprendre

3 couches d'IA : détection d'anomalie statistique → classification ML (XGBoost) → explication par LLM ancrée sur la cause réelle.

⚙️ Agir

Orchestration Camunda (BPMN) qui exécute des actions kubectl réelles, encadrées par une politique de sécurité.

🔁 Clôturer

Vérification post-remédiation, auto-résolution quand la condition disparaît, notification e-mail.

Le principe directeur : une approche hybride — la décision (classification + action recommandée) combine un raisonnement déterministe basé sur la cause racine réelle lue depuis Kubernetes et un score Machine Learning. L'IA n'invente jamais une explication : elle est toujours ancrée sur ce que le cluster rapporte vraiment (ImagePullBackOff, OOMKilled, CrashLoopBackOff, nœud injoignable…).

De bout en bout

Le pipeline complet d'un incident

Du signal brut jusqu'à la résolution : 8 étapes, entièrement automatisées.

#ÉtapeCe qui se passe
1CollectePrometheus fédère les métriques du cluster (CPU/mémoire via cAdvisor, état des objets via kube-state-metrics) ; Loki agrège les logs.
2ScrutationLe backend interroge chaque application surveillée toutes les 120 s (fenêtre d'analyse de 5 min). Une élection de leader garantit qu'un seul réplica scrute (pas de doublons).
3Prédiction IAAppel à /predict : calcul des features → détection d'anomalie (Z-score) → classification XGBoost (incident ? sévérité ? action ?) → explication LLM.
4Création d'incidentSi incident, le backend le persiste (type, sévérité, confiance, cause racine, action recommandée, explication). Un index unique partiel empêche les doublons ouverts.
5Décision auto / humainLa RemediationPolicyService tranche : exécution automatique si la politique est satisfaite, sinon création d'une tâche humaine + e-mail de demande d'approbation.
6OrchestrationUn workflow Camunda (BPMN) est lancé ; un job worker exécute l'action kubectl réelle via le client Kubernetes Java.
7VérificationService de vérification post-remédiation : l'action a-t-elle rétabli la situation ? (avec compensation si échec).
8Auto-résolutionL'IA re-vérifie chaque app ; dès que la condition a disparu, l'incident passe RESOLVED automatiquement + notification.
Le cerveau

Le moteur d'IA en 3 couches

Chaque couche affine la précédente : on détecte d'abord qu'il se passe quelque chose, puis de quoi il s'agit, puis pourquoi et quoi faire.

1

Détection d'anomalie statistique (Z-score)

Repère les écarts anormaux d'une métrique par rapport à son comportement habituel (moyenne ± écarts-types) sur la fenêtre glissante. Premier filtre rapide et non supervisé. Module anomaly/statistical_anomaly.py.

scipynumpy
2

Classification supervisée — XGBoost (3 modèles)

Trois modèles de gradient boosting travaillent ensemble sur un vecteur de 416 features : (a) y a-t-il un incident ? (b) quelle sévérité ? (c) quelle action recommander ? Entraînés sur un jeu de 1 200 échantillons couvrant ~52 scénarios. Modules models/inference.py, features/.

XGBoost 2.1.1scikit-learn 1.5.2pandas / numpy
3

Explication par LLM — Qwen 3B (Ollama)

Génère l'explication « Preuves → Cause racine → Action → Pourquoi » en langage naturel. Point clé : l'explication est déterministe et ancrée sur la cause racine réelle lue depuis kube-state-metrics (ImagePullBackOff, OOMKilled, CrashLoopBackOff, nœud injoignable…). Le LLM n'est qu'un vernis optionnel, validé par un garde-fou (_llm_ok) qui le rejette s'il ne nomme pas la vraie cause — éliminant toute hallucination.

Passage à l'action

Remédiation & orchestration

Politique de remédiation automatique

Une action ne s'exécute automatiquement que si toutes ces conditions sont réunies :

  • automatisation activée
  • action dans la liste autorisée (RESTART_POD, DELETE_CRASHLOOPING_PODS…)
  • action jugée « sûre » (restart, scale, recreate)
  • application & namespace dans l'allowlist
  • confiance ≥ seuil  ·  sévérité ≠ CRITICAL
  • incident non lié à la base  ·  hors période de cooldown

Sinon → tâche humaine + e-mail d'approbation. Les actions consultatives (INVESTIGATE, ESCALATE) ne s'exécutent jamais seules.

Orchestration Camunda 8 (BPMN)

Chaque remédiation est un processus métier modélisé en BPMN :

  • démarrage d'une instance de workflow par incident
  • job workers qui exécutent les tâches techniques
  • tâches utilisateur (validation humaine) intégrées
  • exécution réelle via le client Kubernetes Java (kubectl programmatique)
  • service de récupération de workflow en cas de panne
Camunda 8.8K8s client-java 24.0

Types d'actions de remédiation

RESTART_POD DELETE_CRASHLOOPING_PODS SCALE_DEPLOYMENT SCALE_DOWN FORCE_RECREATE_DEPLOYMENT ROLLBACK INVESTIGATION (consultative) ESCALATION (consultative)

Auto-résolution prouvée : l'incident se referme tout seul. Une élection de leader (bail stocké en base PostgreSQL, TTL 300 s) garantit qu'un seul réplica backend pilote la scrutation et la résolution — évitant tout doublon même avec plusieurs réplicas.
Résilience

Haute disponibilité

La plateforme survit à la perte d'un nœud worker entier : la base bascule, la détection continue, l'incident est enregistré.

Base de données — CloudNativePG

2 instances PostgreSQL (1 primary + 1 replica) sur des nœuds différents. Si le nœud du primary tombe, l'opérateur CNPG promeut automatiquement le replica (~30 s à 1 min). Le service postgres-rw suit toujours le primary courant.

Élection de leader

Bail en base (TTL 300 s) : un seul backend est « leader » et pilote la scrutation. Si son nœud meurt, un autre réplica reprend le bail automatiquement.

Observabilité redondante

Prometheus in-cluster en 2 réplicas (1 par worker, anti-affinité) ; kube-state-metrics épinglé sur le master → la source de détection survit à la perte d'un worker.

Anti-doublons & bascule rapide

Index unique partiel (Flyway V17) sur les incidents ouverts ; tolérances d'éviction rapides (10 s) sur les pods critiques pour accélérer la bascule.

Placement de l'opérateur CNPG (correctif HA)

Pour que la bascule de base fonctionne même quand un worker meurt, l'opérateur CNPG doit survivre : il tolère le nœud master (refuge de secours) mais préfère tourner sur un worker (le master est trop petit). Sans ce correctif, la perte du worker hébergeant l'opérateur bloquait toute bascule.

Validé par test réel (arrêt brutal de VM depuis VMware) :  • worker1 coupé → plateforme maintenue (primary restait sur worker2) → incident NODE_NOT_READY enregistré → auto-résolu au retour.  • worker2 coupé → bascule PostgreSQL automatique ~30 s → plateforme maintenue → incident enregistré → auto-résolu. Aucune cascade.
