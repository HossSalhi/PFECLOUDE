## Architecture cible (HA-01)
- **LB** : HAProxy actif/actif sur `.160` et `.162`, configuration canonique `haproxy/haproxy.cfg` (redispatch, détection rapide, `.153` retiré des backends applicatifs).
- **DNS** : dnsmasq sur `.160` et `.162` ; `dns/helios-dns-health.py` (un par LB, indépendant) publie `helios.orange.tn` et `api.helios.orange.tn` en actif/passif avec hystérésis et fail-open.
- **Placement** : `.153` réservé au control-plane (taint `NoSchedule`), ingress sur `.155`/`.158` uniquement, opérateur CNPG durci (bail leader 60/40 s).
- **Données** : CNPG 2 instances (primaire/réplique sur workers distincts) ; sauvegardes indépendantes : CronJob A (inchangé, PVC `.158`), CronJob B (PVC `.155`), copie hors cluster sur `.161`.
- **Contrôleur web maintenu** : Traefik (provider Ingress NGINX) en remplacement d'ingress-nginx (retiré en mars 2026) — NGINX Gateway Fabric écarté (K8s ≥ 1.31/1.32 exigé, cluster en 1.29).

## Runbook Phase 2b (après GATE-2 validé) — rien n'est lancé avant
Chaque test est lancé en processus détaché : `powershell -File infra\ha01\ops\start_detached.ps1 -Script <script> -Label <étiquette> <arguments>` puis suivi de `results\2026-11-03\<étiquette>.out`.
Attendre ≥ 10 min entre deux tests (retour à l'état sain vérifié par chaque script). Tous les scripts acceptent `--dry-run` (préflight seul).
1. *(optionnel, recommandé)* **B0 — référence en DNS statique** : `p2b_inject.py --mode isolate --lb 160 --label b0` (avant `enforce`) : mesure ce que voient les clients SANS gating, pour chiffrer l'apport de C5.
2. **Enforce** : `p2b_enforce.py --lb 162` puis `p2b_enforce.py --lb 160` (retour arrière automatique en cas d'échec ; manuel : `--rollback`).
3. **Arrêt du service HAProxy** : `p2b_inject.py --mode stop --lb 162 --label s162` puis `--lb 160 --label s160` (300 s chacun).
4. **Isolation de `.160`** : `p2b_inject.py --mode isolate --lb 160 --label i160` (240 s, départ calé juste après un cycle du Bridge HELIOS) → décision **C4**.
5. **GATE-2b** : critères du tableau §F (web/API ≥ 99 % et série ≤ 10 s, API K8s ≥ 99 % et trou ≤ 15 s, 0 transition NotReady, etcd, mémoire…) évalués par chaque script sur 3 points de vue.
   Lecture attendue : en `enforce` le DNS ne publie qu'**une** IP ; un client qui garde sa réponse en cache (point de vue « .161 avec cache ») voit donc une coupure bornée par
   *détection (FALL × période = 9 s) + TTL (30 s)*. Si elle dépasse les seuils, leviers mesurés ensuite : FALL/période/TTL plus courts, ou **faire de `.162` l'IP primaire** (la perte
   de `.160` ne changerait alors AUCUNE réponse DNS) — écart à soumettre à l'utilisateur, jamais appliqué avant mesure.
Filets : minuterie systemd sur la machine visée (rétablit même si le script ou la session disparaît) · abandon automatique (etcd, mémoire, RAM hôte, sondes par nom > 60 s, nœud NotReady > 2 min, canari muet) · rétablissement dans `finally`.

## Constat matériel : gels d'E/S de l'hôte (4 nov. 2026)
Les 5 membres etcd tournent sur 5 VM différentes mais partagent **un seul SSD** (NVMe Intel 512 Go, `C:` occupé à 93 %, 33 Go libres)
et la RAM de l'hôte (~2,3 Go disponibles). Mesures : `python probes/ha01_hoststall.py --hours 30` (3 gels, p99 fsync WAL max 1,8 s / 3,4 s / 7,0 s),
compteurs de fiabilité du disque (`Get-StorageReliabilityCounter` : latence max lecture 5,6 s, écriture 5,9 s, flush 2,1 s).
**Conséquence pour HA-01** : un gel de ~5 s peut survenir pendant n'importe quel test ; il rend `/readyz` de l'apiserver `500` pendant ~3 s
mais ne coupe ni le web ni l'API applicative (latence ≤ 0,44 s). Les rapports distinguent donc *gel de l'hôte* et *effet de la perte de VM* (E6).
**Pistes d'atténuation côté hôte (NON appliquées, à la décision de l'utilisateur, après la campagne)** : libérer ≥ 100 Go sur `C:` (un SSD QLC presque plein perd son cache SLC) ;
déplacer les VM sur un second disque ; vérifier « Fit all virtual machine memory into the reserved host RAM » dans VMware pour éviter le swap des VM.
