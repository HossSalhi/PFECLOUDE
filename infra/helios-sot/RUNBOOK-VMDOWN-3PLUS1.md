4. `pg_rewind` part de ce dernier checkpoint et remonte la chaîne jusqu'à un checkpoint ANTÉRIEUR à la fourche : il lit donc l'enregistrement à `57/87000028`, dans le segment `000000750000005700000087`. **Ce segment est absent de `pg_wal`** (présents : `…75…84`, `…75…85`, `…75…86`, `…75…86.partial`, puis `…76…86/87/88` de la timeline 118 ; aucun `…75…87`).
5. `pg_rewind` le réclame alors à `restore_command` (`/controller/manager wal-restore`), qui n'a **aucune archive WAL** où le chercher (`spec.backup` vide : `archive_mode=on` et `archive_command` « réussissent » — 34 archivages — mais n'archivent rien nulle part) ⇒ `could not restore file "000000750000005700000087" from archive` puis `could not read WAL record at 57/87000028` ⇒ échec, en boucle (3 redémarrages du pod).
6. Ce que le segment manquant contenait n'a pas de valeur (des checkpoints d'arrêt), mais `pg_rewind` ne peut pas le savoir. **Pourquoi il n'est plus sur disque n'est pas établi** (présent à l'écriture du checkpoint à 12:41:28, absent depuis ; les fichiers voisins portent des dates de 12:44:19-22, pendant les premières tentatives de `pg_rewind` ; le journal CSV de PostgreSQL est un tube nommé et ne peut pas être relu après coup). Sans archive WAL, il ne peut de toute façon pas être récupéré.
Conclusion : la réparation n'est PAS « rejouer » ou « réparer » l'ancien volume, mais reconstruire la réplique par `pg_basebackup` depuis le primaire (13 Mo, ≈ 1 à 3 min). Rien d'unique n'est perdu.

**Pourquoi PAS de 3ᵉ instance** : le seul nœud encore éligible serait `.153` (`postgres-7` est sur `.158`, anti-affinité `required` ; `postgres-5` occupe `.155`), mais `.153` porte le taint `node-role.kubernetes.io/control-plane:NoSchedule` (aucun pod PostgreSQL ne le tolère), n'a que ≈ 800 Mo de RAM disponible (kube-apiserver + etcd) et ne doit pas être modifiée.

**Procédure retenue : détacher le volume de l'ancien primaire, puis laisser CNPG cloner** (c'est la logique de `kubectl cnpg destroy --keep-pvc` du code source de l'opérateur 1.28.4 : le Pod et les Jobs de l'instance sont supprimés, le PVC est CONSERVÉ, son `ownerReference` vers le Cluster est retiré, il est annoté `cnpg.io/pvcStatus=detached` et l'opérateur l'ignore ; le plugin `kubectl cnpg` n'est pas installé ici, on fait donc les mêmes gestes à la main).
